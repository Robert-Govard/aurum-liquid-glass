# Подтверждение email при регистрации — дизайн

**Дата:** 2026-09-11
**Статус:** на утверждение

## Контекст

Aurum — самостоятельно хостируемое multi-tenant приложение с открытой
регистрацией (email + пароль, без инвайт-кодов, без модерации). Сейчас
любой может зарегистрироваться на любой email, включая чужой, без какого
бы то ни было подтверждения владения этим адресом. Нужно добавить
подтверждение email — **обязательное** для входа/использования
приложения.

В проекте сейчас **нет вообще никакой инфраструктуры отправки писем**
(проверено: ни SMTP-конфига, ни email-сервиса, ни поля `is_email_verified`
на `User`).

## Global Constraints

- Отправка почты — обычный SMTP через переменные окружения (`AURUM_SMTP_*`),
  без завязки на конкретного провайдера. Реализация — стандартная
  библиотека Python (`smtplib`), новая зависимость не добавляется.
- Верификация обязательна: без неё нельзя войти (`POST /auth/login`
  отказывает отдельным кодом, не тем же, что при неверном пароле).
- **Все уже существующие пользователи при миграции получают
  `is_email_verified = TRUE`** — новое требование действует только для
  новых регистраций, ни один текущий аккаунт не должен потерять доступ.
- Ссылка подтверждения живёт 24 часа.
- Повторная регистрация на email, который уже существует, но не
  подтверждён: если присланный пароль совпадает с сохранённым — письмо
  отправляется заново (без создания второго аккаунта); если не
  совпадает — тот же ответ, что и для уже подтверждённого email (409),
  чтобы нельзя было по разнице в ответе узнать, подтверждён ли
  конкретный email и существует ли он вообще.
- Отдельного эндпоинта "отправить письмо повторно" не заводится —
  кнопка "отправить снова" на фронте — это тот же `register()` с теми
  же email и паролем, что пользователь уже ввёл.
- Каждая строка текста на фронте — через `lib/i18n.ts` (`ru`/`en`,
  синхронно).
- У меня как у ассистента нет ни браузера, ни реального SMTP-сервера для
  проверки — тестирование только через `npm run build`/`pytest` и
  код-ревью; фактическую доставку письма и переход по ссылке нужно
  проверить самостоятельно после того, как в `.env` будут прописаны
  настоящие SMTP-данные.

## Архитектура

### 1. Модель: новые поля на `User`

```python
is_email_verified: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)
email_verification_token_hash: Mapped[str | None] = mapped_column(String(64), nullable=True)
email_verification_expires_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
```

Токен — не отдельная таблица (в отличие от `refresh_tokens`, где у
одного пользователя одновременно живёт МНОГО токенов для разных
устройств): токен подтверждения email всегда один, новый запрос просто
затирает предыдущий. Хранится только SHA-256 хеш (переиспользуется
`core/security.py`'s уже существующая `hash_token()`), как и у
refresh-токенов — сам токен не восстановить из дампа базы.

Миграция для существующих пользователей: `is_email_verified` добавляется
с `server_default=true`, затем дефолт снимается для новых строк (тот же
приём, что уже использован в `f2c8e4a917b3_add_risk_level_to_assets.py`
для NOT NULL колонки с обратной совместимостью) — эффект: существующие
строки получают `TRUE`, а модель на уровне Python (`default=False`)
диктует поведение для новых регистраций.

### 2. Отправка писем

Новый файл `backend/app/services/email_service.py` — синхронная
отправка через `smtplib` (TLS/STARTTLS), запускается через FastAPI
`BackgroundTasks` из роута `/auth/register`, чтобы SMTP-запрос (может
быть медленным или недоступным) не задерживал HTTP-ответ пользователю.
Если `AURUM_SMTP_HOST` не задан — функция просто логирует это и ничего
не отправляет (не роняет запрос — само письмо и так уходит в фоне,
после того как ответ уже отправлен).

Новые переменные окружения (`backend/app/core/config.py`,
`docker-compose.yml`, `.env.example`, по аналогии с уже существующими
`AURUM_COINGECKO_API_KEY`/`AURUM_JWT_SECRET`):

```
AURUM_SMTP_HOST=
AURUM_SMTP_PORT=587
AURUM_SMTP_USER=
AURUM_SMTP_PASSWORD=
AURUM_SMTP_FROM=          # по умолчанию — AURUM_SMTP_USER
AURUM_SMTP_USE_TLS=true
AURUM_PUBLIC_URL=         # публичный адрес, на который ведёт ссылка в письме — свой для каждого self-hosted инстанса
```

Пустой `AURUM_SMTP_HOST` по умолчанию — как и `AURUM_COINGECKO_API_KEY`,
фича просто не работает без реальной настройки, но ничего не ломает.

### 3. Флоу регистрации/входа (backend)

`POST /auth/register` — меняется:
- Email не занят → создаёт пользователя (как сейчас), генерирует токен
  подтверждения, отправляет письмо в фоне.
- Email занят, подтверждён ИЛИ пароль не совпал → `409` (как сейчас).
- Email занят, НЕ подтверждён, пароль совпал → генерирует новый токен
  тому же пользователю, отправляет письмо заново — это и есть "resend".
- **Ответ меняется**: раньше `TokenPair` (сразу логинил), теперь простой
  `{"message": "..."}` — регистрация больше не создаёт сессию, доступ
  появляется только после подтверждения.
- `last_login_at` **больше не проставляется в `register()`** — раз
  регистрация не выдаёт токены, это больше не "вход" в том смысле, в
  каком это поле используется в админке. Проставляется в момент, когда
  сессия реально появляется — то есть при `verify_email()` (см. ниже) и
  при обычном `login()`, как и раньше.

`POST /auth/login` — добавляется проверка `is_email_verified` **после**
существующей проверки пароля (чтобы неверный пароль на неподтверждённом
аккаунте по-прежнему давал общий `401`, не намекая, что аккаунт вообще
существует и в каком он состоянии):

```python
if user is None or not user.is_active or not verify_password(password, user.password_hash):
    raise HTTPException(status_code=401, detail="Incorrect email or password")
if not user.is_email_verified:
    raise HTTPException(status_code=403, detail="Email not verified")
```

Новый `POST /auth/verify-email` (тело: `{"token": "..."}`) — ищет
пользователя по хешу токена, проверяет срок действия, помечает
`is_email_verified = True`, чистит поля токена, проставляет
`last_login_at`, **сразу возвращает `TokenPair`** — меньше трения:
перешёл по ссылке — и уже внутри приложения. (Для Android это работает
лишь отчасти: ссылка из письма откроется в обычном браузере телефона, а
не внутри самого приложения — токены осядут там же, в браузере. Это
некритично: подтверждение всё равно засчитается, и войти в само
приложение можно будет обычным способом сразу после. Отдельный deep-link
для этого не делаем — не запрашивалось.)

### 4. Frontend

`lib/auth.ts`:
- `register()` — больше не сохраняет токены; возвращает новый исход
  `AuthResult` `"verify_email_sent"`.
- `login()` — новый исход `"email_not_verified"` при `403`.
- Новая функция `verifyEmail(token)` — вызывает `/auth/verify-email`, при
  успехе сохраняет токены и обновляет состояние сессии (как
  `login()`/`register()` сейчас) — `LoginGate` реактивно переключится на
  само приложение, без дополнительного кода на этой стороне.

`AuthScreen.tsx` — два новых состояния в уже существующем экране
входа/регистрации:
- после регистрации: сообщение "проверьте почту" вместо мгновенного
  входа.
- после неудачного входа с `email_not_verified`: сообщение + кнопка
  "отправить письмо ещё раз", вызывающая тот же `register(email,
  password)` с уже введёнными данными.

Новый экран `components/auth/VerifyEmailScreen.tsx` — читает `?token=`
из URL, вызывает `verifyEmail()`, показывает состояние
(проверяю/успех/ошибка — истёк или неверен токен). `LoginGate.tsx`
получает одну дополнительную ветку: если нет сессии и путь —
`/verify-email`, рендерит этот экран вместо `AuthScreen` (тот же
`useLocation()`, что уже доступен благодаря `BrowserRouter` в
`main.tsx`).

## Тестирование

- Backend: новые тесты в `test_auth.py` — вход с неподтверждённым email
  даёт `403` (не `401`); подтверждение по правильному токену
  логинит и включает `is_email_verified`; просроченный/несуществующий
  токен — ошибка; повторная регистрация на неподтверждённый email с
  верным паролем не создаёт второго пользователя и обновляет токен;
  с неверным паролем — тот же `409`, что и для подтверждённого email
  (не давая распознать разницу).
- Frontend: как и весь фронтенд в проекте — `npm run build`, без
  тестового фреймворка. Реальную доставку письма, переход по ссылке и
  визуальные состояния экранов нужно проверить самостоятельно после
  того, как в `.env` появятся настоящие SMTP-данные.

## Вне скоупа (явно)

- Восстановление забытого пароля ("forgot password") — отдельная,
  незапрошенная фича, не путать с подтверждением email.
- Deep-link, открывающий саму Android-сборку по клику на ссылку в
  письме (сейчас ссылка всегда открывается в обычном браузере).
- Ограничение частоты повторных запросов письма (rate limiting) — при
  текущем масштабе (несколько пользователей на личном инстансе) не
  требуется; если понадобится позже — отдельная задача.
