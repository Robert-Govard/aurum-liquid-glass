# Админ-панель — дизайн

**Дата:** 2026-09-11
**Статус:** на утверждение

## Контекст

Aurum — multi-tenant SaaS-приложение (JWT-аутентификация по аккаунтам,
полная изоляция данных между пользователями). Владельцу приложения нужен
способ видеть список зарегистрированных пользователей, управлять ими
(включать/выключать, удалять) и видеть их статистику (активность +
финансовые суммы).

**Важное открытие на этапе исследования:** backend для админки уже
полностью реализован и покрыт тестами, заложен ещё на этапе Auth
Foundation, но никогда не имел фронтенда:

- `User.is_admin` / `User.is_active` (модель `backend/app/models/user.py`).
- `GET/PATCH/DELETE /api/admin/users` (`backend/app/api/routes/admin.py`),
  защищены зависимостью `get_current_admin` (403 без прав админа).
- `backend/app/services/user_service.py`: `list_users`, `update_user`
  (переключает `is_active`, отзывает refresh-токены при выключении),
  `delete_user` (каскадно удаляет ВСЕ данные пользователя — FK
  `ondelete="CASCADE"` на каждой таблице).
- `backend/scripts/promote_admin.py` — единственный способ сделать
  пользователя админом (CLI, не через API — осознанное решение: открытая
  регистрация без инвайт-кодов означает, что self-service "стать админом"
  через API было бы уязвимостью).
- `backend/tests/test_admin.py` — 5 тестов, все проходят.
- Фронтенд уже получает `is_admin` в объекте пользователя после логина
  (`frontend/src/lib/auth.ts`), просто нигде не используется.

Из нового нужно добавить: статистику по пользователям (эндпоинта для неё
нет вообще) и весь фронтенд.

## Global Constraints

- Не трогать существующие защищённые тестами эндпоинты `PATCH`/`DELETE
  /api/admin/users/{id}` в их текущем поведении — только добавить проверку
  "не на себя" (см. ниже).
- `/api/auth/me` (обычный self-view) не должен получить новых полей —
  расширяется только ответ `GET /api/admin/users`.
- Статистика считается батчем (агрегирующими SQL-запросами по всем
  пользователям сразу), а не в цикле "по одному запросу на пользователя" —
  иначе список из N пользователей стоит N обращений к БД.
- Тема Aurum и уже существующие компоненты (`Card`, `Switch`, `GroupedList`,
  `Dialog`) переиспользуются на фронтенде без изменений их публичного API.
- Подтверждение удаления — обычный `window.confirm`, как везде в
  приложении (осознанное решение пользователя, не усиленное подтверждение).
- Каждая строка текста — через `lib/i18n.ts` (`ru`/`en`, синхронно).

## Архитектура

### 1. `last_login_at` — новое поле на `User`

```python
last_login_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
```

Новая Alembic-миграция (голова сейчас — `43a4507fff95_make_user_id_not_null`),
добавляющая nullable-колонку (backfill/default не нужен — `NULL` для
существующих пользователей корректен, они просто "ни разу не логинились
после этого обновления").

Проставляется в `backend/app/services/auth_service.py`:
- В `login()` — сразу перед `_issue_token_pair`.
- В `register()` — тоже сразу перед `_issue_token_pair`: первая регистрация
  засчитывается как первый вход, иначе свежезарегистрированный
  пользователь показывал бы в админке "никогда не входил" до первого
  повторного логина, что вводит в заблуждение.

Не обновляется в `refresh()` — "последний вход" означает явные события
входа/регистрации, а не молчаливое продление сессии по refresh-токену.

### 2. Статистика — батч-агрегация по всем пользователям

Новый файл `backend/app/services/admin_stats_service.py` (не в
`user_service.py` — это не операции над строкой `User`, а агрегация по
`Account`/`Transaction`/`Asset`/`AssetValuation`, отдельная зона
ответственности):

```python
async def get_user_stats(session: AsyncSession) -> dict[int, UserStats]:
    """Возвращает {user_id: UserStats} для ВСЕХ пользователей сразу.
    Батч, а не цикл: список админки не должен стоить N обращений к БД на
    N пользователей."""
```

где `UserStats` — простой Pydantic/dataclass со полями `accounts_count: int`,
`transactions_count: int`, `net_worth: Decimal`.

Реализация тремя агрегирующими запросами:

1. **Кол-во счетов**: `select(Account.user_id, func.count(Account.id)).group_by(Account.user_id)`.
2. **Кол-во транзакций**: аналогично по `Transaction.user_id`.
3. **Текущий капитал** (наличные + активы прямо сейчас, БЕЗ дневной
   истории — это упрощённая версия того, что уже считает
   `net_worth_service.get_net_worth_summary()` для одного пользователя с
   графиком; здесь нужна только сегодняшняя сумма для ВСЕХ сразу):
   - Наличные: те же правила, что и в `net_worth_service` (переиспользовать
     константу `CASH_ACCOUNT_TYPES` оттуда, чтобы определение "что
     считается наличными" не разъехалось в двух местах) — один проход по
     ВСЕМ счетам и ВСЕМ транзакциям (без фильтра по пользователю; это
     единственное осознанно межпользовательское чтение во всём проекте —
     ровно то, для чего и существует админка), накапливая
     `defaultdict(Decimal)` по `user_id` вместо одной переменной.
   - Активы: последняя оценка (`AssetValuation`) на каждый `asset_id`,
     через оконную функцию `row_number() OVER (PARTITION BY asset_id ORDER
     BY as_of_date DESC)`, затем сумма по `Asset.user_id`.
   - `net_worth = наличные.get(user_id, 0) + активы.get(user_id, 0)`.

### 3. API: расширение `GET /api/admin/users`

Новая схема `backend/app/schemas/user.py`:

```python
class AdminUserRead(UserRead):
    last_login_at: datetime | None
    accounts_count: int
    transactions_count: int
    net_worth: Decimal
```

`list_users()` в `user_service.py` меняет тип возврата на
`list[AdminUserRead]` — вызывает `get_user_stats()`, сама строит объекты
`AdminUserRead` (данные `User` + словарь статистики, с 0/0/0 по умолчанию
для пользователей без единого счёта/транзакции). Роут
`GET /admin/users` — `response_model=list[AdminUserRead]`.

`PATCH`/`DELETE` эндпоинты не меняют форму ответа, только добавляют
проверку "не на себя" (следующий пункт).

### 4. Защита от самоблокировки

`update_user()` и `delete_user()` в `user_service.py` получают новый
параметр `acting_admin_id: int`. Если `user_id == acting_admin_id` —
`HTTPException(400, "Cannot modify your own account")` (английский текст —
как и остальные `detail` в этом файле, `"User not found"` и т.д.; это
serverside-сообщение не для конечного пользователя и не проходит через
`lib/i18n.ts`, который относится только к фронтенду). Роуты
`update_user_route`/`delete_user_route` в
`routes/admin.py` получают явный параметр
`current_admin: User = Depends(get_current_admin)` (уже используется на
уровне роутера — FastAPI переиспользует закешированный результат, а не
считает зависимость дважды) и передают `current_admin.id`.

На фронтенде — та же защита превентивно: в строке таблицы,
соответствующей текущему админу (`user.id === currentUser.id`), кнопка
удаления и переключатель активности не рендерятся вообще (не просто
disabled — чтобы не провоцировать "а что будет, если нажать").

### 5. Frontend

Новая страница `frontend/src/pages/AdminPage.tsx` — список пользователей
карточками (`Card`, как везде), для каждого: email, бейджи
админ/неактивен, дата регистрации, последний вход (или "ещё не входил",
если `null`), кол-во счетов, кол-во транзакций, капитал
(`formatCurrency`), и (кроме своей строки) `Switch` для
активен/неактивен + кнопка удалить с `window.confirm`.

Новый хук `frontend/src/hooks/useAdmin.ts` (React Query, тот же паттерн,
что и остальные хуки: `useUsers()`, `useUpdateUser()`, `useDeleteUser()`),
дергающий `/api/admin/users`.

**Навигация:** в `lib/navigation.ts` `NavItem` получает новое опциональное
поле `adminOnly?: boolean`; пункт "Админка" добавляется в `NAV_ITEMS` с
`adminOnly: true`. `Sidebar.tsx`, `MobileTabBar.tsx` — оба места, что
строят список пунктов из `NAV_ITEMS`, фильтруют
`item.adminOnly && !user?.is_admin` перед рендером (текущий пользователь
уже доступен в обоих компонентах транзитивно через `useAuthState()`,
которым уже пользуется `Topbar.tsx` — паттерн уже есть в кодовой базе).
Обычный пользователь не увидит пункт "Админка" нигде — ни в сайдбаре, ни
в "Ещё" на мобильном.

## Тестирование

- Backend: новые тесты для `get_user_stats()` (несколько пользователей с
  разным набором счетов/транзакций/активов — проверить, что суммы не
  утекают между пользователями) и для защиты "не на себя" (админ пытается
  выключить/удалить сам себя — должен получить 400, а не 200/204).
  Существующие 5 тестов в `test_admin.py` не должны сломаться (новые поля
  в ответе — аддитивное изменение, старые проверки не завязаны на точный
  набор ключей).
- Frontend: как и весь фронтенд в этом проекте, тестового фреймворка нет —
  проверка через `npm run build` и код-ревью. У меня как у ассистента нет
  браузера/устройства для визуальной проверки — открыть и попробовать
  вживую стоит самостоятельно (переключить чужого пользователя в
  неактивного, убедиться что своя строка не редактируется, проверить, что
  обычный пользователь не видит пункт "Админка").

## Вне скоупа (явно)

- Self-service "стать админом" — остаётся только через
  `scripts/promote_admin.py`, как и было спроектировано изначально.
- Усиленное подтверждение удаления (например, ввод email) — решили
  оставить обычный `window.confirm`.
- История/график капитала конкретного пользователя в админке — только
  текущая сумма, не полноценный `NetWorthPage` на чужие данные.
- Просмотр детальных транзакций/счетов конкретного пользователя админом —
  не запрашивалось, только агрегированные счётчики.
