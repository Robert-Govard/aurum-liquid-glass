# Просмотр дашборда пользователя из админки — дизайн

**Дата:** 2026-09-11
**Статус:** на утверждение

## Контекст

Админ-панель (список пользователей, статистика, вкл/выкл, удаление) уже
сдана и смержена. Пользователь просит расширение: клик по строке в
списке открывает всплывающее окно с дашбордом этого пользователя — те
же 4 карточки статистики, что и на обычной странице Дашборд, с
переключателем месяц/год.

**Ключевое открытие на этапе исследования:** `dashboard_service.get_dashboard_summary(session, year, month, user_id)`
уже параметризован по `user_id`, а не привязан к текущему
залогиненному пользователю — та же архитектура, что и у
`net_worth_service.get_net_worth_summary`, которую админ-панель уже
использовала для подсчёта капитала. Это делает всю задачу почти
чистым переиспользованием: новый эндпоинт — это по сути проверка "такой
пользователь существует" плюс вызов уже существующей, уже
протестированной функции.

Список транзакций (`GET /transactions`) в отличие от дашборда жёстко
завязан на `current_user.id` прямо в теле роута — но он в эту задачу
не входит: пользователь явно выбрал только 4 карточки статистики, без
последних транзакций и без разбивки по категориям донат-диаграммой.
Это сознательно сужает скоуп и избавляет от необходимости писать
что-либо для транзакций вообще.

## Global Constraints

- Один новый backend-эндпоинт, никакой новой бизнес-логики — только
  переиспользование `get_dashboard_summary`.
- Список годов для переключателя в попапе — не отдельный запрос, а
  диапазон от года регистрации пользователя (уже есть в `AdminUser.created_at`)
  до текущего года, посчитанный на фронтенде.
- Капитал/суммы показываются в валюте ПРОСМАТРИВАЕМОГО пользователя
  (`AdminUser.currency`, уже есть в ответе `/admin/users` после
  недавнего фикса), а не валюте админа — та же ошибка уже была найдена
  и исправлена один раз для капитала в списке, здесь тот же принцип
  применяется с самого начала.
- Никаких новых i18n-ключей — все тексты карточек статистики берутся из
  уже существующих `dashboard.*` ключей (то же самое, что использует
  обычная страница Дашборд).
- Переиспользуются существующие компоненты: `Dialog`, `StatCard`,
  `MonthSelector`, `YearSelector` — без изменений их публичного API.
- Модальное окно должно оставаться смонтированным при закрытии, чтобы
  сработала уже существующая анимация закрытия `Dialog` (см. ниже,
  архитектура) — родитель не должен размонтировать компонент попапа
  сразу при сбросе выбранного пользователя.

## Архитектура

### 1. Backend: один новый эндпоинт

`backend/app/api/routes/admin.py` — новый роут в том же файле, что и
остальная админка (защищён тем же `get_current_admin` на уровне
роутера):

```python
GET /api/admin/users/{user_id}/dashboard-summary?year=&month=
```

Логика: получить `User` по `user_id` (404, если не найден — та же
проверка, что уже есть в `update_user`/`delete_user`), затем вызвать
`get_dashboard_summary(session, year, month, user_id)` и вернуть
результат как есть. Схема ответа — уже существующая `DashboardSummary`,
новая схема не нужна. Параметры `year`/`month` — с теми же дефолтами
(текущий год/месяц) и границами, что и у обычного
`GET /dashboard/summary`.

### 2. Frontend: модальное окно + подключение к списку

Новый компонент `frontend/src/components/admin/AdminUserDashboardModal.tsx` —
обёртка вокруг `Dialog`, всегда смонтирована в `AdminPage` (не
пересоздаётся при каждом открытии/закрытии — иначе анимация закрытия
`Dialog`, основанная на внутреннем таймере, не успеет доиграть, так как
React уничтожит сам компонент `Dialog` раньше, чем истечёт таймер).
Держит `open = user !== null`, но содержимое рендерит по внутреннему
`displayUser`, который обновляется только когда `user` не `null` — так
заголовок и данные не мигают в пустоту в момент закрытия, пока идёт
анимация.

Внутри — переключатель месяц/год (`MonthSelector`/`YearSelector`,
диапазон лет — от года регистрации просматриваемого пользователя до
текущего года) и те же 4 `StatCard`, что и на `DashboardPage`, только
суммы форматируются в валюте просматриваемого пользователя
(`AdminUser.currency`), а не текущего админа.

Новый хук `frontend/src/hooks/useAdmin.ts`: `useAdminUserDashboard(userId: number | null, year, month)` —
`enabled: userId !== null` (тот же паттерн, что уже используется в
`useCrypto.ts`/`useReports.ts` для условных запросов), чтобы не
дёргать бэкенд, пока ни один пользователь не выбран.

`AdminUserList.tsx` получает новый проп `onView: (user: AdminUser) => void` —
блок с email/бейджами/датами/статистикой каждой строки становится
кликабельной кнопкой, вызывающей `onView(user)`. Переключатель
активности и кнопка удаления остаются как есть (в соседнем, а не
вложенном элементе — кнопка внутри кнопки невалидна).

`AdminPage.tsx` держит `selectedUser: AdminUser | null` и рендерит
`AdminUserDashboardModal` рядом со списком.

## Тестирование

- Backend: новый тест на `/admin/users/{id}/dashboard-summary` —
  доступен только админу (403 для обычного пользователя, как и весь
  остальной `/admin/*`), 404 для несуществующего `user_id`, и
  корректно возвращает данные ИМЕННО целевого пользователя, а не
  вызывающего админа (изоляция — тот же тип проверки, что уже есть для
  статистики в списке).
- Frontend: как и весь фронтенд в этом проекте, тестового фреймворка
  нет — `npm run build` плюс код-ревью. Визуальная проверка (открытие
  попапа, анимация, переключение месяца/года) недоступна в этой среде.

## Вне скоупа (явно)

- Последние транзакции пользователя в попапе — не выбрано.
- Разбивка по категориям (донат-диаграмма) в попапе — не выбрано.
- Любые действия из попапа (редактирование чужих данных) — попап
  только для просмотра.
